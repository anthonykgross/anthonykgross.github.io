## Problem Statement

Quand un recruteur pose une question à un moteur de réponse IA (ChatGPT Search, Perplexity, Claude avec recherche web), le profil d'Anthony K GROSS doit pouvoir ressortir sous la bonne facette : **hands-off** (Head of Engineering) pour une requête managériale, **hands-on** (Principal Engineer) pour une requête technique. Aujourd'hui, le site n'expose aucun signal machine. Il n'y a ni `robots.txt`, ni `sitemap.xml`, ni JSON-LD, ni `canonical`/`hreflang`. De plus, `<html lang>` et `og:locale` valent `en-US` sur toutes les pages, y compris les pages FR (`_layouts/default.html:2` et `:15`).

## What Makes This Cool

Le CV existe déjà sous forme de données (`_data/cv_{hands_off,hands_on}_{fr,en}.yml`). On ne réécrit rien : on ajoute des *vues machine* générées au build depuis la même source. Un LLM qui atterrit sur le site lit des faits structurés (une personne, deux facettes, des compétences, des expériences) au lieu d'interpréter des divs Tailwind. Bonus : la vue Markdown de chaque variante sert aussi le cas « un recruteur colle une fiche de poste et l'URL du CV dans son assistant ».

## Constraints

- Jekyll statique. **Déploiement constaté** (`.github/workflows/deploy.yml`) : l'Action se déclenche sur push `main` **et sur `pull_request`**. Elle fait `mv -f _config_prod.yml _config.yml` (les deux configs ne sont **pas fusionnées**, la config prod *remplace* la config dev), lance `jekyll build` dans `jekyll/builder:latest`, puis `actions/deploy-pages` **sans condition**. Le build n'est pas fait par GitHub Pages natif, donc n'importe quel plugin du Gemfile est utilisable (c'est déjà le cas de `jekyll-postcss`).
- Conséquence : toute clé globale ou tout plugin ajouté doit figurer **dans les deux configs**. Les faits globaux vont dans `_data/`, pas dans une config.
- Pas de JS côté client, pas de JS inline (règle du repo).
- Les YAML restent la **source unique**. Aucun format machine n'est écrit à la main. Quand une donnée machine manque, on l'ajoute dans `_data/`.

## Premises

1. Le levier principal est l'identité sans ambiguïté : JSON-LD `Person` + `sameAs` (LinkedIn, GitHub, YouTube, Twitter). `llms.txt` n'est qu'un complément peu coûteux. Plusieurs études de logs en 2026 montrent que les crawlers IA ne le demandent presque jamais ([1clickreport](https://www.1clickreport.com/blog/llms-txt-evidence-2026), [OtterlyAI](https://otterly.ai/blog/the-llms-txt-experiment/)), et Google a dit ne pas le supporter.
2. **(Révisée pendant la session.)** Les crawlers d'**entraînement** sont bloqués. Ceux de **recherche / à la demande** sont autorisés. La visibilité passe donc par la recherche en direct, pas par la mémoire du modèle. Conséquence acceptée.
3. Les 4 pages décrivent **une seule entité** (`@id` = `https://anthonykgross.fr/#person`). Les propriétés de `Person` sont **identiques sur toutes les pages**, et la facette ne s'exprime que par la page (`ProfilePage`) et par l'`Occupation` qu'elle met en avant.
4. Les YAML restent la source unique, et tout format machine est généré au build.
5. Le site seul ne suffit pas : la cohérence avec LinkedIn et GitHub (même titre, même ville, lien retour) compte autant. C'est hors du code.

## Recommended Approach

**Approach B : CV lisible par les machines.** A + JSON-LD riche généré depuis les YAML + une vue `.md` par variante + `llms.txt` + assertions en CI. Effort M (humain ~2-3 j / CC ~1 h 30, vérifications CI comprises). Le JSON Resume et `llms-full.txt` sont **hors périmètre** de cette itération : aucun consommateur identifié.

### 1. Corrections de base (`_layouts/default.html`)
- `<html lang="{{ page.lang | default: site.lang }}">`.
- `og:locale` dérivé de `page.lang` (`fr_FR` / `en_US`), plus `og:locale:alternate` pour l'autre langue.
- `<link rel="canonical" href="{{ site.url }}{{ page.url }}">`.
- `hreflang` par variante, pas de `x-default` global :
  - Pages hands-off : `fr` → `/`, `en` → `/en/cv`, `x-default` → `/`.
  - Pages hands-on : `fr` → `/cv/hands-on`, `en` → `/en/cv/hands-on`, `x-default` → `/cv/hands-on`.
- `<meta name="description" content="{{ page.description }}">`.
- `<link rel="alternate" type="text/markdown" href="{{ page.md_url }}">`.

### 2. `robots.txt` (fichier Liquid à la racine, `sitemap: false`)
```
User-agent: GPTBot
User-agent: ClaudeBot
User-agent: CCBot
User-agent: Google-Extended
User-agent: Applebot-Extended
User-agent: meta-externalagent
Disallow: /

User-agent: *
Allow: /

Sitemap: {{ site.url }}/sitemap.xml
```
Le groupe `*` autorise tout le reste : recherche, à la demande, moteurs classiques. Limite assumée : un futur bot d'entraînement non listé sera autorisé tant que la liste n'est pas mise à jour.

### 3. `sitemap.xml`
- Ajouter `jekyll-sitemap` au Gemfile et à `plugins:` **dans `_config.yml` et dans `_config_prod.yml`**.
- Les pages générées par `jekyll-redirect-from` sont exclues par le plugin. Les vues `.md`, `robots.txt` et `llms.txt` portent `sitemap: false`.
- Résultat attendu : exactement 4 URL (les pages canoniques).

### 4. JSON-LD (`_includes/jsonld.html`, inclus dans le `<head>`)
Un `@graph` par page :
- `Person` (`@id` stable, **nœud strictement identique sur les 4 pages**). Règle : chaque propriété vient de `_data/person.yml` ou des **YAML EN**, quelle que soit la langue de la page.
  - `name`, `image`, `knowsLanguage`, `address` (`PostalAddress`, `addressLocality` = city, `addressCountry` = `country_code`) : depuis `_data/person.yml`. `url` = `site.url`, et `sameAs` = boucle sur `site.socials` (présent dans les deux configs).
  - `jobTitle: ["Head of Engineering", "Principal Engineer"]`.
  - `knowsAbout` = union des `category` de `skills` (hands-on EN + hands-off EN) et de `management_skills` (hands-off EN), dédupliquée.
  - `hasOccupation` = deux `Occupation` : « Head of Engineering » (`skills` = lignes de `management_skills` + `skills` de hands-off EN) et « Principal Engineer » (`skills` = lignes de `skills` de hands-on EN). Une ligne YAML = une valeur, sans découpage.
- Expériences : **pas d'historique dans le JSON-LD** (reporté, eng review D1). Le parcours reste lisible en texte dans les vues `.md`. Le poste actuel affiche son vrai intitulé (`Senior Software Engineer`). Les facettes décrivent le positionnement recherché, pas l'intitulé du poste actuel. Ce choix est assumé.
- `ProfilePage` (`@id` = URL de la page) : `inLanguage`, `name` = titre de la variante, `description` = `objectives` de la variante, `mainEntity` → `#person`, `about` → l'`Occupation` de la facette de la page.
- Toutes les valeurs texte passent par le filtre `jsonify`. On ne concatène jamais de chaîne brute.

### 5. Vues Markdown
- 4 fichiers aux `md_url` du tableau, générés par un layout `cv-markdown` qui lit `site.data[page.cv_data]`. Le layout doit produire du texte brut : fichier source `.md` avec `layout: cv-markdown`, et le layout ne passe pas le contenu au convertisseur (le permalien finit en `.md`). **Point à vérifier en premier au build.** Si Jekyll convertit quand même, utiliser une source `.txt` avec un permalien en `.md`.
- **Liste blanche** des champs exposés : `title`, `objectives`, `profile.languages`, `profile.projects`, `skills`, `management_skills`, `experiences` (date, entreprise, poste, missions, compétences), `certifications`. Les champs `profile.status` et `profile.interests` sont **exclus** des vues machine (JSON-LD et `.md`). Ils n'aident pas la recherche et risquent d'être cités hors contexte.

### 6. `llms.txt`
Un index court : qui, la ville, les deux facettes, et les liens vers les 4 vues `.md` et les 4 pages HTML.

### 7. Assertions en CI (workflow existant)
Ajouter une étape **après** « Build the site » et **avant** « Upload Pages artifact » dans le workflow de déploiement. Le build a donc déjà lieu avec `_config_prod.yml`, et les URL sont en `https://anthonykgross.fr`. Un script Ruby `bin/check-machine-views.rb`, exécuté dans le conteneur `jekyll/builder` (Ruby et la lib standard `yaml`/`json` y sont, aucune dépendance ajoutée) :
- Fichiers (constatés dans `_site`) : `index.html`, `cv/hands-on.html`, `en/cv.html`, `en/cv/hands-on.html`. **Un fichier manquant fait échouer le build.**
- Extraction du JSON-LD : l'include émet exactement un bloc `<script type="application/ld+json">`, avec la balise ouvrante, le JSON et la balise fermante sur des lignes séparées. Le script l'extrait par regex multiligne, exige **exactement un** bloc par page, puis `JSON.parse`. Le build échoue si le JSON est invalide, si le **nœud `Person` complet** diffère entre les 4 pages ou si une URL contient `localhost`.
- `lang` et `canonical` attendus par page, et réciprocité des `hreflang` (grep).
- `robots.txt` : le groupe d'entraînement contient `Disallow: /`, et le groupe `*` ne contient pas `Disallow: /`.
- `sitemap.xml` : exactement les 4 URL canoniques.
- `_site/docs` et `_site/bin` n'existent pas (eng review D3).
- **Non-régression du rendu visible** (eng review D4) : sur chaque page, « Marseille, France » est présent, et le nombre de blocs d'expérience est égal au nombre d'entrées `experiences` du YAML de la page.
- Vues `.md` et JSON-LD : aucune balise `<` dans les `.md`, et aucune valeur de `profile.status` ou `profile.interests`. Ces valeurs sont lues dans les 4 YAML par le script (`YAML.load_file`), jamais codées en dur.
- `<title>` de chaque page = titre de sa facette (voir le tableau en section 0).
- Vérification **manuelle**, une fois après la mise en prod : Schema.org Validator et Rich Results Test.

Note : la cible `make build` (dev, `-it`) n'est pas utilisée en CI. Pour reproduire la CI en local, il faut **reproduire le remplacement**, pas une fusion : build dans une copie où `_config_prod.yml` remplace `_config.yml` (par exemple une cible `make build-prod`), puis lancer le script.

### R2-1 — feasibility

**Problem**

> Section 0, section 3 and Next Steps 1 add `site.person` and the `jekyll-sitemap` plugin to `_config.yml` only. **Remedy**

> Put the person facts in a data file (for example `_data/person.yml`) so they are not tied to a config file, and add `jekyll-sitemap` to `plugins:` in both config files (or merge configs in the workflow instead of replacing the file). Make the local check reproduce exactly what CI does.

### R2-9 — feasibility

**Problem**

**Remedy**

> Fix the include's output format (opening tag, JSON and closing tag on separate lines, exactly one block per page) and assert that one block is found. Alternatively, extract it with an HTML-aware tool such as Ruby/Nokogiri in the Jekyll image.
